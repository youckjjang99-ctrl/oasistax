# OASIS CRM v9.8.9 적용 안내

이 패치는 DB발굴의 사용자별 저장기능을 유지하면서 업체별 전사 공통 배정·연락상태를 추가합니다. 검색·상세 조회만으로는 업체를 선점하지 않으며, `내 영업DB에 담기`에서만 배정과 기존 영업DB 저장이 실행됩니다.

## 핵심 동작

- 사업자번호 → 법인번호 → 국민연금 관리번호 → 정규화된 업체명+주소+전화번호 순으로 `company_uid`를 생성합니다.
- 검색 후보의 원천 식별값을 서버의 canonical UID resolver로 일괄 확인하고, 강한 식별값이 일치할 때만 기존 source identity를 채택합니다. 서로 다른 강한 식별값이 충돌하면 저장·배정하지 않습니다.
- 신규 저장은 `oasis_claim_and_save_company_sales_assignment` 한 번으로 배정과 기존 `oasis_prospect_companies` 저장을 같은 DB 트랜잭션에서 처리합니다.
- 저장 도중 오류가 나면 두 변경이 함께 롤백되며, 선배정 후 별도 저장·보상 해제 방식은 사용하지 않습니다.
- A와 B가 동시에 저장하면 DB 잠금과 고유제약으로 한 명만 성공합니다.
- 미접촉 임시배정은 기본 24시간, 사용자별 기본 한도는 30건입니다.
- 실제 연락결과가 저장되면 담당자가 확정되고 연락횟수·최초/최근 연락일이 갱신됩니다.
- 검색 결과에서 한 업체를 선택해 `내 영업DB에 담고 연락결과 기록`을 바로 실행할 수 있습니다.
- `번호오류` 업체는 정규화된 전화번호 집합이 실제로 바뀐 경우에만 재활성화됩니다.
- 번호오류 지문에는 기존 영업후보뿐 아니라 연결된 `oasis_employment_contacts`의 휴대전화·유선전화도 포함합니다.
- 기존 매일 연락처 보강 작업은 카카오·네이버 단계까지 함께 비교해 같은 업체를 중복 선점하지 않으며, 네이버 일시 오류 건은 완료 처리하지 않고 네이버 재시도 대기열에 유지합니다.

## 적용 순서

1. 현재 GitHub `main`, 운영 DB와 Railway 환경변수를 백업합니다.
2. 패치 ZIP의 변경 파일을 프로젝트 루트에 그대로 덮어씁니다.
3. `RUN_v9.8.9.bat`를 실행해 파일·문법·테스트를 확인합니다.
4. Supabase SQL Editor에서 `supabase_v1032_company_sales_assignments.sql`을 실행합니다.
5. `supabase_v1032_company_sales_assignments_rls.sql`을 실행해 신규 객체의 RLS와 권한을 재적용합니다.
6. 테스트 계정 A·B와 관리자 계정으로 10개 요구 시나리오를 검증합니다.
7. GitHub `main`에 반영하고 Railway 배포상태를 확인합니다.

`RUN_v9.8.9.bat`는 운영 Supabase나 Railway를 자동 변경하지 않습니다.
검증 성공 후에도 본 마이그레이션 SQL을 먼저, RLS SQL을 다음 순서로 운영자가 직접 적용해야 합니다.

## 영업사원 사용방법

1. DB발굴에서 기존 방식으로 검색합니다. 조회이력만 기록되며 담당자는 지정되지 않습니다.
2. 연락할 업체를 선택하고 `내 영업DB에 담기`를 누릅니다.
3. 선택 업체가 한 곳이면 검색 결과의 `선택 업체 연락결과 바로 기록`도 사용할 수 있습니다.
4. 임시배정한 업체는 `저장된 영업후보`에서 메모와 연락결과를 관리합니다.
5. `재연락 요청`은 다음 연락예정일 입력이 필수입니다.
6. 이미 본인에게 배정된 업체는 중복 저장되지 않으며 기존 저장목록에서 확인합니다.
7. 다른 담당자가 먼저 배정한 업체는 즉시 제외되고 검색 결과를 새로고침합니다.

## 관리자 사용방법

1. `관리자 > 시스템 관리 > 영업배정 관리`를 엽니다.
2. 전체 통계는 서버 집계 결과로, 업체목록은 100·200·500건 페이지 단위로 확인합니다.
3. 업체별 담당자, 상태, 최초 조회·배정·연락, 최근 연락, 만료시간과 연락횟수를 확인합니다.
4. `이관 충돌` 목록에서 기존에 여러 사용자에게 저장됐던 업체의 최종 담당자를 지정합니다.
5. 담당자 변경, 강제 해제·회수, 재활성화, 영구 제외에는 변경사유를 입력합니다.
6. 사용자별 미접촉 배정 한도를 조정하고 감사로그를 확인합니다.

## 기존 데이터 보존

- 기존 업체 ID, 영업후보, 검색이력, 메모, CRM, 상담일지를 삭제하지 않습니다.
- 기존 상담일지는 실제 연락로그로 멱등 이관하고 담당자·연락횟수·최초/최근 연락일을 복원합니다.
- 여러 담당자가 연결된 기존 업체는 임의로 삭제하거나 승자를 정하지 않고 관리자 충돌 목록에 유지합니다.
- 기존 저장 데이터는 `legacy_hold`로 보호해 최초 마이그레이션 직후 임의 만료시키지 않습니다.

## 보안 주의

- 신규 테이블은 RLS를 활성화하고 직접 클라이언트 접근을 차단합니다.
- 일반 사용자는 본인 배정·메모·담당 업체 연락이력만 확인할 수 있습니다.
- 다른 사용자의 이름·상담내용은 일반 검색결과에 노출하지 않습니다.
- Supabase `service_role` 키는 Railway 서버 환경변수에만 보관하고 화면·로그·패치에 넣지 않습니다.

## 배포 전 필수 확인

- A 단순 조회 후 B에게도 검색되는지
- A 저장 직후 B에게서 제외되는지
- A/B 동시 저장 시 한 명만 성공하는지
- 24시간 미접촉 만료가 해제되는지
- 연락기록 후 담당이 확정되는지
- 거절·연락불가·번호오류 재활성화 기준이 지켜지는지
- 일반 사용자의 타 담당 URL 직접 접근이 차단되는지
- 관리자 담당 변경과 감사로그가 남는지
- 기존 메모·상담일지·충돌 원본이 보존되는지
- 연락처 보강 작업의 카카오·네이버 단계 경쟁 방지와 네이버 오류 재시도가 유지되는지
