# OASIS CRM v9.13.0-crm-consistency

작업 기준: origin/main `4db662cbc5f7ac04a22b118dd1246b54bc2f6e1b`.
작업 브랜치: `codex/crm-consistency-20260909`.
기존 프로젝트 폴더의 미커밋 변경은 그대로 보존하고 별도 worktree에서 작업합니다.

## 작업 순서와 범위

1. 동시 저장 충돌 방지: 로컬 파일 트랜잭션, 고객 revision 검사, 클라우드 versioned RPC, 초안·재전송 보존.
2. 기기 간 동기화: 로컬 유무와 무관한 소유자 범위 클라우드 갱신, 미전송 변경·편집 중 값 보호.
3. 연락상태 조회 정확성: 현재 페이지 업체의 최신 연락 결과, 재배정 이후 이전 담당자 이력 비노출.
4. 반복 조회 최적화: 사용자 범위의 짧은 읽기 캐시, 해당 사용자 저장 성공 시 무효화, 오류 재시도.

각 단계의 테스트를 통과한 뒤 다음 단계 구현을 시작합니다. 경정청구·Tilko·유료 자료수집 호출·전화번호 수집 로직은 변경하지 않습니다.

## 1단계 설계

로컬 CRM 전체 파일을 읽고 다시 쓰던 경합을 프로세스/스레드 파일 잠금으로 보호합니다. 이미 열린 편집 화면의 고객 revision이 바뀌었으면 저장을 거부하고 내 초안을 `_local_conflicts`에 보존합니다. 다른 고객의 변경은 영향을 받지 않습니다. JSON이 손상되었을 때 빈 CRM으로 간주하고 덮어쓰지 않습니다. 기존 타임라인 80건 저장 제한은 제거하되 화면 표시량은 유지합니다.

기존 `oasis_crm` 테이블·ID·business_no·customer_id·crm_data는 그대로 사용합니다. `crm_version bigint`와 사용자/수정시각/ID 인덱스를 추가하고, 저장 요청을 보존하는 `oasis_crm_save_requests`를 추가합니다. 요청 ID, 소유자, 대상, 기준 버전, 제안 변경분·추가 이력, 결과, 생성/수정시각을 저장합니다. 기존 고객행과 원천자료를 삭제하거나 정규화해 다시 쓰지 않습니다.

`oasis_save_crm_versioned` RPC는 같은 고객의 신규/갱신 저장을 트랜잭션 잠금으로 직렬화합니다. 오래된 버전의 필드 수정은 충돌 처리하고, 이력 추가는 기존 이력을 유지합니다. 동일 요청의 재전송은 멱등 처리합니다. 요청 내용은 전용 테이블에 보존하며 일반 로그에 출력하지 않습니다.

이 프로젝트는 Railway의 사용자 로그인 + 서버 서비스 역할을 사용합니다. 신규 테이블은 RLS를 켜고 `PUBLIC`/`anon`/`authenticated`의 직접 접근을 차단합니다. RPC는 `SECURITY INVOKER`이고 서비스 역할만 실행할 수 있습니다. 사용자 소유자 범위는 로그인한 사용자로 정하는 기존 서버 경로를 유지합니다. 브라우저에 서비스 키를 전달하지 않습니다.

안전한 전환을 위해 구버전의 `oasis_crm.crm_data` 직접 INSERT/UPDATE는 DB 가드가 거부합니다. 기존 버전 없는 대기열도 자동 덮어쓰기하지 않고 검토 대상으로 보존합니다. 따라서 마이그레이션은 신버전 배포와 함께 승인된 점검 시간에 적용해야 하며, 구버전과 장기간 혼용하면 일부 CRM 클라우드 저장이 대기 상태가 됩니다. 새 RPC를 적용하지 않은 환경에서 앱은 로컬 초안/동기화 대기로 안내합니다.

## 2단계 설계와 사용법

로컬 CRM 파일이 있다는 이유로 클라우드 확인을 생략하던 동작을 제거했습니다. 홈·기업관리센터·누적 고객DB·AI 코파일럿 화면 실행 시 사용자별 60초 간격으로 CRM 갱신을 확인합니다. 화면을 아무 조작 없이 열어 둔 동안의 실시간 push가 아니라 **화면 실행/재실행 시 갱신**입니다. 수동 최신본 조회는 60초 제한을 건너뜁니다.

소유자 조건과 `(updated_at, id)` 커서로 페이지를 읽으며, 서버의 응답 건수 제한으로 페이지가 짧아져도 빈 페이지가 나올 때까지 확인합니다. 조회 실패, 잘못된 응답, 중복 키, 안전 조회 상한 초과 시 완료 체크포인트를 갱신하지 않습니다. 현재 안전 상한은 한 번에 50,000개 CRM 행이며 이를 넘으면 완료가 아닌 확인 필요 상태로 알립니다.

5분 겹침 조회와 24시간마다 전체 재확인을 병행합니다. 트랜잭션 시작 시각과 실제 commit 순서가 다른 경우를 고려한 안전장치이며, 5분보다 오래 지연된 commit은 다음 전체 재확인 또는 수동 새로고침까지 반영이 늦을 수 있습니다. 이는 변경 스트림을 신설하지 않고 기존 구조를 보존하는 방식의 제한입니다.

미전송 로컬 변경·클라우드 기준본·새 클라우드 자료를 비교합니다. 같은 값으로 수렴하면 저장 확인으로 처리하고, 새 독립 필드는 병합합니다. 기존 필드의 편집 의도가 모호하거나 서로 다르게 변경되었으면 양쪽을 보존하고 충돌로 표시합니다. 값을 바꿨다가 원래 값으로 다시 바꾼 편집도 보호하기 위해 자동 병합보다 보수적으로 판단합니다. 기존 프로필 확장값과 중복 횟수를 포함한 상담 이력을 유지합니다.

고객관리 CRM 양식의 **초안 보관 후 최신본 불러오기**는 제출되지 않았던 입력값까지 보관한 후 확인된 최신 필드를 불러옵니다. 기업관리센터에서는 **최신 CRM 다시 불러오기**, 충돌 시 **클라우드 최신본 불러오기 · 내 초안 보관**을 사용합니다. 조회에 실패하면 입력과 편집 기준을 그대로 유지합니다. 로컬에만 있는 실제 상담 이력은 최신본 채택 시에도 타임라인에 남고 미전송 상태로 유지됩니다. 보관된 초안은 해당 고객 CRM의 초안 펼침 영역에서 확인할 수 있습니다.

이번 동기화 대상은 CRM 상태·메모·예정일·프로필·상담 이력입니다. PDF 원문, 재무 원천값, 로컬 누적 Excel 전체를 자동으로 덮어쓰지 않습니다. 기존 고객 Excel의 초기 클라우드 복원 경로는 그대로 유지합니다.

## 3단계: 연락상태 조회 정확성

이전 화면은 전체 연락기록 중 최근 1,000건을 먼저 가져온 뒤 업체별 상태를 계산했습니다. 다른 업체의 기록이 많아지면 오래된 업체의 실제 최신 연락결과를 놓칠 수 있었습니다. 새 목록 RPC는 각 업체의 현재 배정에 해당하는 연락기록을 서버에서 직접 요약합니다. 목록과 대시보드가 같은 분류 조건을 사용합니다.

재배정 전 담당자의 기록은 일반 사용자의 현재 담당 업체 요약에 섞이지 않습니다. 현재 담당자·작성자·배정주기를 함께 검사하며 관리자의 전체 조회 권한은 유지합니다. 과거 연락일을 나중에 입력한 정상 기록은 생성시각으로 배정주기를 판단합니다. 기존 마이그레이션 보존 상태(`legacy_hold`)도 유지합니다.

현재 배정의 최근 연락일·다음 연락일과 전체 누적 연락일을 구분합니다. 최신 결과 정렬은 연락일, 생성일, 기록 ID 순서로 결정합니다. 잘못된 응답이나 목록 페이지 누락은 정상 0건으로 숨기지 않고 재조회가 필요한 오류로 안내합니다. 상세 연락기록은 캐시하지 않고 매번 서버 권한을 확인하는 기존 경로를 사용합니다.

## 4단계: 반복 조회 최적화

재무·등기 스냅샷은 큰 JSON 본문만 사용자·프로젝트·자료 종류별로 최대 20초 캐시합니다. 캐시를 재사용할 때도 서버에서 해당 행의 소유자와 수정시각을 새로 확인합니다. 소유권이 바뀌거나 행이 사라지면 이전 본문을 반환하지 않으며, 확인 실패도 캐시된 성공으로 바꾸지 않습니다. 저장 성공과 대기열 재전송 성공 시 해당 사용자의 캐시만 무효화합니다.

회사명·법인번호로 찾은 보조 조회 결과와 구형 사업자 키는 캐시하지 않습니다. 원격에서 같은 이름의 후보나 우선순위가 높은 정상 키가 새로 생겼을 때, 기존 행의 수정시각이 그대로여도 후보 유일성과 조회 우선순위를 다시 확인합니다.

합성 테스트에서 같은 스냅샷을 10회 읽을 때 전체 본문 조회는 1회, 작은 메타데이터 확인은 9회였습니다. 이는 **전송 본문을 줄이는 개선**이며 전체 HTTP 호출이 10회에서 1회로 줄었다는 뜻은 아닙니다. 운영 데이터로 측정한 응답속도 개선율은 아직 없습니다.

영업 조회와 업무함의 짧은 캐시는 사용자·권한·변경 세대를 분리합니다. 상세정보·상담 원문·연락이력은 캐시로 권한을 대신 판단하지 않습니다. 오류와 부분 응답은 정상 결과로 캐시하지 않습니다. 일반 사용자 A의 저장이 무관한 B의 캐시를 모두 초기화하지 않도록 하고, 관리자 이관처럼 이전 담당자를 안전하게 특정하기 어려운 변경은 별도 안전 무효화 경로를 사용합니다.

캐시 무효화 세대는 프로세스 내에서 공유됩니다. 다른 Railway 인스턴스에는 즉시 전파되지 않으므로 일부 요약은 TTL까지 늦어질 수 있습니다. 고객 상세와 원문 접근 권한 확인은 이 요약 캐시와 분리되어 있습니다. Redis·Realtime 등 별도 기반시설은 이번 패치에서 추가하지 않습니다.

특히 다른 인스턴스에서 담당자를 바꾸면 기존 업무함의 업체명·예정일 요약이 최대 20초 남을 수 있습니다. 상담 원문은 업무함 캐시에 넣지 않습니다. 모든 인스턴스에서 0초 내 요약 제거를 보장하는 변경은 아닙니다. 기존 업무함 캐시 30초를 20초로 줄인 것입니다.

## 사용자·관리자 사용법

- 일반 사용자는 기존 CRM 저장 버튼을 그대로 사용합니다. 다른 저장과 충돌하면 내 초안을 보관하고 최신본을 확인한 뒤 필요한 값을 다시 저장합니다.
- 초안 보관 메시지와 클라우드 저장 완료 메시지를 구분해 확인합니다. 로컬 임시 저장이나 동기화 대기는 다른 기기에 반영 완료된 상태가 아닙니다.
- 내 영업DB의 연락결과·다음 연락일은 현재 배정 기준으로 확인합니다. 재배정된 업체에서 이전 담당자의 메모를 일반 사용자에게 새로 노출하지 않습니다.
- 관리자는 실패 대기열 중 구버전 CRM 직접 쓰기와 버전 충돌을 검토합니다. 검토 없이 전체 데이터를 강제 덮어쓰지 않습니다. 자동 재시도 한도에 도달한 작업도 삭제하지 않습니다.
- 별도 가입·권한·고객 ID 변경은 필요하지 않습니다. 신규 화면 구조를 도입하지 않고 기존 저장·조회 흐름에 경고와 최신본 불러오기를 보완했습니다.

## 운영 적용 원칙

운영 마이그레이션, GitHub push 및 Railway 배포는 별도 승인 전에는 수행하지 않습니다. 이 문서는 개발 중 설계와 검증 범위를 설명하며, 운영 반영 완료를 의미하지 않습니다.

롤백 시 고객자료를 삭제하지 않습니다. 먼저 새 저장 경로를 유지한 상태에서 문제를 확인하고, 구버전으로 돌아가야 하면 CRM 쓰기를 일시 중지한 후 DBA 검토 하에 가드 트리거만 해제합니다. `crm_version`, 저장 요청 이력, 고객행은 남깁니다. 구버전의 마지막 저장 우선 동작으로 돌아가므로 동시 수정 위험이 다시 생깁니다. 강제 push와 Git 이력 재작성은 필요하지 않습니다.

### 승인 후 적용 순서

1. 대상 main 커밋을 다시 확인하고 패치 이후 변경과 충돌하는지 검토합니다. 작업 폴더에 이미 있는 미커밋 파일을 통째로 덮어쓰지 않습니다.
2. 운영 고객·CRM·배정·연락기록·대기열의 건수와 ID/내용 지문을 읽기 전용으로 확보하고, 기존 백업 복구 가능 상태를 확인합니다.
3. 운영과 같은 격리 Supabase 환경에서 두 SQL의 권한·PostgREST 응답을 검증합니다. 이번 로컬 PostgreSQL 검증은 이 운영 통합 절차를 대신하지 않습니다.
4. CRM 저장 점검 시간을 확보하고 두 SQL 적용과 신버전 배포를 연이어 수행합니다. 전화번호 수집 테이블·대기열·경정청구 인증 절차는 변경하지 않습니다.
5. 로그인, 일반/관리자 권한, CRM 저장·충돌·두 기기 갱신, 내 영업DB·연락기록·업무함, 기업등록·컨설팅·경정청구·AI·파일 다운로드, PC/모바일 메뉴를 확인합니다. 유료 인증/수집 테스트는 별도 승인 없이 호출하지 않습니다.
6. 전후 데이터 건수·지문 감소나 권한 회귀가 있으면 완료 처리하지 않고 새 쓰기를 중지하여 원인을 확인합니다. 원본행·Storage·Git 이력은 삭제하지 않습니다.

### 패치와 실행 파일

패치 ZIP은 변경 파일만 원래 상대경로로 포함하고 상위 폴더나 `.git`을 포함하지 않습니다. 로컬 고객자료·비밀키·PG 실행파일·테스트 데이터베이스·캐시는 포함하지 않습니다. `RUN_v9.13.0-crm-consistency.bat`는 전체 pytest, 개인정보 유입 검사, diff 검사를 실행하며 SQL 적용·Git push·배포는 하지 않습니다. 기존 프로젝트의 Python 의존성 환경이 필요합니다.

로컬 DB 검증 스크립트는 임의 운영 DB에 연결하지 못하도록 loopback 주소·전용 포트·합성 테스트 사용자·데이터 디렉터리를 제한합니다. PG 런타임과 클라이언트를 별도로 준비한 개발 환경용이며 BAT에서 자동 실행하지 않습니다.

아래 업로드 명령은 **승인 후 main에 이번 변경만 안전하게 반영하고, 무관한 변경이나 개인정보가 없는 것을 확인한 작업 폴더**에서 사용합니다. 현재 worktree에서 그대로 main을 push하면 이번 미커밋 변경이 배포되지 않습니다.

```bash
git status
git add .
git commit -m "feat: improve CRM consistency and read performance"
git push origin main
```

테스트는 합성 자료와 로컬 테스트 서버를 사용했습니다. 실제 고객·인증정보·유료 수집 API로 검증하지 않았습니다. 테스트 성공은 운영 배포 성공을 의미하지 않습니다.

이번 무손실 저장 개선의 주 대상은 CRM 상태·메모·프로필·상담이력입니다. 재무·등기 본문은 조회 캐시만 보완했으며, PDF 재분석의 필드별 승인·재무 버전 복원·원문 전체의 실시간 동기화는 이 패치에서 신설하지 않았습니다. 레거시 등기 보조 식별의 5,000행 상한과 이름 복구 시 개별 고객 조회도 기존 경로로 남아 있습니다.

- 관련 회귀에서 기존 `test_direct_sales_customer_ui`가 main에서도 실패함을 확인했습니다. 이미 도입된 요약 조회 래퍼를 거치도록 기대값을 수정하고, 래퍼가 실제 조회 함수로 연결되는지도 검사합니다. 기능을 삭제하거나 테스트를 생략한 것이 아닙니다.
- 전체 테스트 수집 단계에서 기존 Daum 검토 테스트가 main에 없는 이전 SQL 파일명을 참조함을 확인했습니다. 실제 추적 중인 SQL 파일명으로 테스트 경로만 수정했습니다. 전화번호 수집 기능과 SQL 내용은 바꾸지 않았습니다.
- 전체 UI 테스트와 Windows spawn 테스트를 함께 실행할 때 Streamlit 테스트가 남긴 임시 `__main__.__file__`을 자식 프로세스가 다시 실행하는 문제가 있었습니다. 동시 저장 테스트가 자기 합성 테스트 모듈을 불러오도록 격리했습니다. 실제 4개 프로세스/48개 이력 검증은 그대로 유지합니다.
- 연락이력 화면 테스트는 제거된 전역 요약 조회까지 2회 호출을 기대하던 조건을 업체 상세 1회 + 서버 요약 경로로 바꿨습니다. 상세 활동 이력이 입력 양식보다 먼저 나타나는 검증은 유지했습니다.
- 로컬 PostgreSQL 검증은 Windows PostgreSQL 17.10이며 운영 Supabase 17.6과 메이저 버전은 같습니다. 실제 Supabase Auth/PostgREST/Railway 운영 통합 검증과 완전히 동일하지 않습니다.
